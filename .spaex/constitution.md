- For supported Python versions, prefer modern built-in generics such as `list[str]` and `dict[str, int]`; use abstract collection types such as `Mapping` for read-only inputs when they describe the contract better. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_

- Model data explicitly, using a small `dataclass`, `Enum`, or dedicated value object when a concept has invariants. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Prefer simple, readable control flow: comprehensions are appropriate for small transformations, and a normal loop is appropriate when conditions, side effects, or error handling would make the comprehension difficult to read. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Prefer the standard library and existing project dependencies before adding a new package, and keep any dependency addition justified by a real capability or maintenance benefit rather than a shorter one-off expression. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Raise specific exceptions and catch only exceptions that can be handled at that layer. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Use context managers for resources such as files, locks, and transactions. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Assert the exception type and meaningful details without over-specifying incidental message formatting. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep parametrized cases focused and readable; add a new case when it demonstrates a distinct boundary or regression. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep tests easy to read, fast enough to run frequently, and honest about what they do not cover, since a passing test is evidence only for the behavior it actually exercises. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep the test level visible in the test's location and name according to the repository convention. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Make fixture setup and cleanup explicit, using context managers and framework cleanup hooks so a failing test cannot leak files, connections, processes, or patches into the next test. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Test coroutines with the project's supported async test tooling, and test cancellation, timeout, cleanup, and ordering assumptions when they affect correctness. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Use `unittest` or the project's chosen test framework consistently. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep unsafe code isolated and justified: prefer a safe abstraction around a small unsafe block, document the safety argument, and add a test that would expose a violation of the assumed invariant. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Prefer iterators and combinators when they make the transformation clearer, but use an ordinary loop when it communicates control flow or error handling better; idiomatic syntax is not a reason to make code harder to read. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Prefer types that make invalid states unrepresentable, using enums for a closed set of states and `Option<T>` for an explicitly optional value. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Respect ownership instead of fighting it: borrow when the callee does not need ownership, and return owned data when the result must outlive the input. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Use `Result<T, E>` for recoverable failures, propagate errors with `?`, and add context at a boundary where it helps the caller understand what failed. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Before handing off a change, run the repository's formatter, static checks, and relevant tests — in Rust, `cargo fmt --check`, `cargo check`, `cargo clippy`, and `cargo test` when the project supports those commands, respecting the repository's configured Clippy lint levels and enabling stricter categories or `-D warnings` only when the project deliberately requires them, and following documented command variants when they differ — and report what was run. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`, `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep public APIs and module interfaces narrow and intentional: document public items when the crate's lint policy requires it, hide implementation details behind the smallest stable API callers need, and avoid exposing implementation details, re-exporting everything, or creating pass-through modules solely to work around a local borrow, lifetime, or boundary problem. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`, `com.github.haexmas.atoms.general-coding/general-coding`]_
- Cover boundaries and failure behavior deliberately: empty and malformed input, relevant limits, authorization decisions, persistence failures, and cancellation or concurrency behavior where applicable. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- For async code, use the async test support of the runtime already used by the project; test cancellation, timeout, and ordering assumptions when they affect correctness. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Keep test helpers small and local to the tests that own them; a shared fixture is justified when it expresses a stable domain setup, not merely to remove a few repeated lines. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Keep tests deterministic and isolated; inject clocks, ports, and external clients where the behavior needs control. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Keep the test suite readable, fast enough to run often, and trustworthy when it passes, since a test suite is production code. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Prefer explicit assertions with useful failure context. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Run `cargo test` for the complete package or workspace as appropriate; this includes unit, integration, and library documentation tests by default, so follow project-specific feature, target, and test-runner requirements too. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Test behavior and contracts — observable behavior and important failure paths — rather than mirroring private implementation details; a test is useful only when it can fail for a real regression, including when the promised behavior regresses. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`, `com.github.haexmas.atoms.general-coding/general-coding`]_
- A file should have one primary reason to change; split a file when it has unrelated responsibilities, independent public concepts, different change owners, or tests that are difficult to isolate. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Comments should explain why a non-obvious decision exists, what invariant must be preserved, or which external constraint applies; update comments when the behavior changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Give each function one coherent responsibility at one level of abstraction; extract a helper when it gives a meaningful name to a concept, makes a branch independently testable, or removes repeated logic, not merely because the function crossed an arbitrary line count. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep dependencies directed and understandable: avoid circular imports, hidden global state, and a domain layer that knows about infrastructure details, and put I/O, framework adapters, and process wiring at the edges when the architecture calls for such a separation. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep each change self-contained and easy to review: production code, relevant tests, documentation, and configuration belong together when they describe the same behavior, and split independent refactors and unrelated cleanups into separate changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep each task isolated in its own worktree and topic branch so that changes can be reviewed, tested, committed, and removed independently. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep related tests close to the behavior they verify according to the language and repository convention; a module split is not complete if its tests, documentation, fixtures, and call sites are left misleadingly behind. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep side effects at visible boundaries; pure calculations and decisions should be easy to test without a database, network, filesystem, clock, or global mutable state. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Name code after its domain meaning and behavior; a clear name is better than a comment that explains an otherwise opaque `data`, `helper`, or `process` function. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Organize code around cohesive domain or feature boundaries where the codebase supports it. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer a change that clearly improves maintainability and correctness over theoretical perfection; when a design is uncertain, make the smallest reversible change that provides evidence about the next decision. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer early returns or named helpers when they make the main path easier to follow, and reduce nesting. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Refactor repeated behavior when the shared rule is real and the abstraction makes both callers clearer; keep the abstraction close to the domain that owns it, and avoid a generic utility module becoming a dumping ground. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Separate broad formatting or mechanical refactors from behavior changes when possible, since mixed diffs make review, debugging, rollback, and blame less reliable. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Treat a change of about 100 net lines as a useful review-size warning and a change approaching 1000 lines as a strong prompt to split the work or agree on the larger change in advance; generated code, mechanical renames, and required migrations are legitimate exceptions, but should be identified as such. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Use smaller soft thresholds as prompts for review, not as automatic failures: a function or method beyond roughly 40–60 lines, or nesting deeper than roughly three levels, deserves a deliberate look at whether it is still one coherent unit or has distinct responsibilities to separate, since these thresholds are heuristics, not targets or mandatory limits. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- When a repository already has a documented structure, naming scheme, or size convention, follow it unless the task explicitly changes that convention; these defaults are not a reason to reformat or reorganize an entire codebase. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- For any question about the codebase — what something does, where it lives, how pieces relate, which existing artifact might already satisfy a request, or how to trace a symptom back to its source, including exploratory lookups incidental to a larger task — run a bounded graphify context-map query (`graphify query "<intent>" --budget <N>`) before a raw `grep`/`rg` search or broad file reads; the only exemption is a local one-file edit at a symbol whose location is already known from earlier in the same task, and authoring a new named artifact remains governed by the graphify-first-authoring consultation rule even when a context map would be unnecessary. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- The resulting context map should preserve, when available, the task intent and token budget, the selected files and symbols, the relevant edge or call relationship, source locations for every claim, and an explicit truncation or failed-consultation note. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- When running a context-map query, state the concrete intent as a question, choose a small token budget (starting around 800–1500 tokens and increasing only if the returned relationships are insufficient), use `--dfs` for a narrow dependency path or `graphify path`/`graphify explain` for one specific relationship or symbol, treat the result as a map by extracting cited locations, symbols, and relationships and then reading only the smallest necessary source slices, and — if the result is truncated or ambiguous — narrow the question or make one additional focused query rather than compensating with a full repository dump. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- As rough guidance rather than a hard cutoff — operator judgment overrides — six or more identical lines sharing the same logic across candidates should prompt an extract-and-refactor proposal. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Treat a new function name that closely resembles an existing one, a third similar date/retry/validation/error-handling utility with slightly different semantics, copying ten or more lines to adapt slightly, the thought "similar but different enough," or starting to type a generic helper without having checked the graph, as signals to stop and run the consult step before proceeding. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Before writing any code, first read the task and the code it touches and trace the real flow end to end; then, stopping at the first rung that holds, climb: skip building it if it is not needed (YAGNI); reuse a helper, util, or pattern that already exists in the codebase rather than rewriting it; use the standard library; use a native platform feature; use an already-installed dependency; write it as one line if possible; only then write the minimum code that works. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Prefer deletion over addition, boring solutions over clever ones, and the fewest files possible; prefer the shortest working diff, but only once the problem is understood — a small change made in the wrong place isn't lazy, it's a second bug; question complex requests by asking whether a simpler existing option already covers the need; and when two equally-sized standard-library approaches are available, pick the edge-case-correct one rather than the flimsier algorithm. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- When fixing a bug, address the shared root cause rather than only the symptom named in the report: grep every caller of the function being touched and fix the shared function once, rather than patching only the path the ticket names and leaving a sibling caller still broken. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_

## SHOULD_NOT

- Do not apply a blanket rewrite merely because the pattern matches. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- Do not install a package automatically to obtain `ast-grep`, and do not make adoption of this molecule fail solely because the optional tool is absent. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- Avoid circular dependencies, and do not introduce a barrel export or a new abstraction only to shorten an import path. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not assume that a platform-specific global or API exists everywhere. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not leave promises unhandled. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not use `||` when a valid value such as `0`, `false`, or `""` must be preserved, and do not hide a required value behind optional chaining without deciding how absence is handled. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not use mutation or shared mutable module state as an accidental communication channel. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Avoid `any` in TypeScript and `Any` in Python; prefer a precise type, a generic, a protocol, or `unknown` followed by explicit narrowing instead. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not catch an error merely to log it and rethrow or re-raise it unchanged, and do not catch an exception to hide a failure; that usually duplicates logs and loses ownership of the failure decision. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not replace the repository's configured tooling with a personal global installation, do not claim that checks or tests passed without actually running them, and do not assume a test file is exercised unless the runner configuration confirms it discovers and runs it. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Do not leave floating promises in tests, and do not let a test pass before the asynchronous work it is meant to verify has completed. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Do not turn every test into a slow end-to-end test. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Do not mock the unit or code under test so heavily that the test only proves the mock's own wiring or setup rather than real behavior. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Do not rely on real network calls or services, shared mutable state, uncontrolled randomness, order dependence, or arbitrary timer sleeps to make a test pass or to wait for concurrency. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Avoid clever metaprogramming when ordinary functions and classes suffice. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Avoid expensive work, network access, and surprising side effects at module import time unless the project explicitly uses that pattern. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not call blocking I/O or CPU-heavy work directly from an event loop. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not pass a growing collection of positional tuples or unrelated dictionary keys through the application. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not use a bare `except`, catch `Exception` to hide a failure, or return `None` as an undocumented substitute for an error. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not call `asyncio.run()` from code, production or test, that may already be running inside an event loop. _[from `com.github.haexmas.atoms.coding-guideline-python/python`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Do not hide unrelated scenarios inside a large fixture or broad parameter matrix. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Avoid weakening a production invariant merely to make a test convenient; make the fixture satisfy the same contract as a real caller. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- As rough guidance rather than a hard cutoff, fewer than five purely structural lines (setup, error-wrapping, adapter boilerplate) should not be over-extracted, and hits inside test files should not be touched unless they are helper functions. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Avoid adding a new dependency when it can be avoided, and avoid adding boilerplate that nobody asked for. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_

## MAY

- An existing project may opt out of individual TypeScript strict-mode checks during migration. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- A `.clone()` may be used when it expresses a real ownership boundary or is demonstrably the clearest and sufficiently cheap choice. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- `unwrap()` or `expect()` may be used when an invariant is local, explicit, and genuinely impossible to violate, provided that invariant is documented at the call site. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- A language-required test-module declaration or registration — such as Rust's `#[cfg(test)] mod tests;` — may remain in the module or file under test, with the test implementation itself kept in the separate test file. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`, `com.github.haexmas.atoms.general-coding/general-coding`]_
- Generated files, vendored code, snapshots, and other files not normally edited by hand may exceed the 500 LoC boundary, but should be excluded from this assessment. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- The operator may suspend the graphify-consultation rule for the current session via any natural-language request expressing that intent (for example "skip graphify check"); such suspension does not persist across sessions and must be re-issued each new session, and even while suspended, the agent must still note in its response which artifacts it would have flagged had the rule been active. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
